# ガイドの情報設計

## 基本階層

サイトの主な導線は次の階層で考える。

1. ホーム：ガイドの目的と読み始める入口
2. 全体像（Business）：何を守り、どんな活動が必要か
3. 業務の分類（Domain）：目的や機能が近い業務のまとまり
4. 業務フロー（Process）：一つの仕事の開始から受渡しまで

Evidence と Insight は、標準的な業務ガイドと混ぜず、それぞれ観察事実と分析として扱う。

## サイドメニュー

サイドメニューはファイル一覧ではなく、読者が理解する順序と分類を表す。

- ページの役割とMarkdownに書かれた分類関係をサイドメニューへ反映する。メニューの階層に合わせるためだけにディレクトリを移動しない。
- 一覧、分類、個別業務で同じ業務名を使う。
- Domain の下に、そのDomainを主領域とするProcessをまとめる。
- Processを一つの長いフラット一覧にしない。
- 一覧ページは入口と比較に使い、個別ページの内容を重複掲載しない。
- 一つのProcessが複数Domainに関係しても、メニュー上の所属は主領域を一つ決める。関連領域は本文のリンクで表す。
- 表示順は永続 ID、業務の自然な理解順、サイト内の既存規則のいずれかで一貫させる。

`scripts/site-config.mjs` は、業務分類ページの見出しを分類名に使い、個別業務の `- 主領域：[DOMAIN-xxx：…]` から所属を読み取る。個別業務の主領域がない・複数ある・参照先がない場合はビルドが失敗する。一覧ページは別扱いのため、変更前にスクリプトを確認する。表示名や所属だけを直接ハードコードせず、Markdownを正本として更新する。

## ページを分ける基準

次のいずれかに当てはまる場合は、ページ分割を検討する。

- 読者の目的が異なる内容が同居している。
- 一つのページに、開始条件や成果が異なる複数の仕事がある。
- 背景説明のために、本題へ到達しにくい。
- 見出しだけでは全体を把握できず、関連箇所を往復する必要がある。

短いことだけを理由に統合しない。反対に、同じ判断を理解するための内容を細切れにしない。

## 見出し

- `#` はページの題名に一つだけ使う。
- `##` は読者の問いに対応する大きな区切りに使う。「入力」より「必要な情報」、「終了条件」より「どこまでできれば完了か」のように書く。
- 見出しだけを順に読んでも、ページの説明順が分かるようにする。
- 「概要」「詳細」だけで済ませず、同種ページで意味が揃う名前を使う。
- 深い見出し階層で問題を隠さない。階層が深くなる場合はページの責務を見直す。

## リンクと導線

- 「こちら」ではなく、移動先で分かる内容をリンク文字列にする。
- 一覧から個別ページへ、個別ページから前後業務へ移動できるようにする。
- ファイルや見出しを変更した場合は `rg` でリポジトリ内の参照元を検索し、変更後のリンク先へ更新する。
- 旧URLや旧見出しリンクの互換性は保証しない。互換性のための旧アンカーや転送ページの追加・維持は必須としない。
- 永続 ID はページ名や配置を変えても維持する。
- 関連リンクを増やしすぎず、業務上の受渡しや理解に必要な関係を優先する。

## 変更後の確認

少なくとも次の入口から対象ページへ到達できるか確認する。

- ホームから全体像
- 全体像から業務の分類
- 業務の分類から個別の業務フロー
- 個別の業務フローから前後の業務

PC表示だけでなく、列数の多い表や長いメニューがスマートフォンで理解できるかも確認する。

ナビゲーション、リンク変換、表示を変更した場合は、`npx playwright test` で関連する検索・リンク・スマートフォンのメニューの動作を確認する。実行環境とサイトの構成は `pages/README.md` を参照する。
