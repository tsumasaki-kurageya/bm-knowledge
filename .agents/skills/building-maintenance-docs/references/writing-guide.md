# 読みやすい業務ガイドの書き方

## 読者と目的

| 項目 | 設定 |
| --- | --- |
| 誰が読むか | ビルメン業務SaaSチームの営業、カスタマーサクセス、商品企画、開発、事業責任者 |
| 読む目的 | SaaSが解決したい顧客業務と周辺業務を理解する。顧客が何を目指し、何に苦労しているかを理解し、その達成に寄与するSaaSを作れること |
| 前提知識 | ビルメン業者が携わる領域には多少知識がある。全職種が所有者側の計画・費用判断や専門分野まで詳しいとは仮定しない |

テーマは所有者・管理者・作業者などの立場をまたぐ建物維持保全の業務全体とする。読者の所属と、調べる顧客の役割を混同しない。顧客を特定の業種・役職だけに固定しない。

プロジェクトの会話・Issue・作成経緯は前提にしない。初歩の用語説明を繰り返すより、仕事の目的、判断、他の担当への引継ぎを説明する。専門用語や略語は、隣接領域の読者にも分かる短い説明を初出時に付ける。

ページを読んだ後に、少なくとも次が分かる文章にする。

- 何のための仕事か
- 何をきっかけに始まるか
- 誰がどの役割で関わるか
- 何を確認・判断・実施するか
- 何が残り、次のどの仕事につながるか
- 顧客が望む結果と、作業や書類の完成はどう違うか
- 困りごとの有無・影響を確かめるには何を聞くか

## 顧客理解とSaaSへのつなげ方

顧客の困りごとは、公開資料に基づく業務上のリスクと、現場で確認した事実を区別する。現場の根拠がないときは「顧客に確認したいこと」として質問を書く。「二重入力が多い」「承認が遅い」などを一般的な実態として補わない。

確認するのは、誰がどの場面で困るか、そのためにどの仕事や判断が進まないか、頻度・手間・影響、現在の対処方法。必要な質問を業務ごとに選び、同じチェックリストを全ページへ複製しない。

SaaSへの示唆を記載する場合は、支援する業務と目指す結果を示す。効果・機能・優先順位が未検証ならその旨を残す。技術的な判断、承認、責任の所在を、システム機能の存在だけで置き換えない。

## 言葉の選び方

- 日常語で意味が保てる場合は日常語を使う。「実施する」より「行う」、「当該」より「その」を検討する。
- 専門用語が必要なら、最初に短く説明する。用語を言い換えただけの定義にしない。資料の正式名称・法令用語・引用の意味を変えない。
- 組織名ではなく役割を書く。「ビルメン会社が判断する」ではなく、何を判断できる役割かを示す。
- 名詞を連ねず、誰が何をするかを動詞で書く。
- 一文では一つの判断または動作を扱う。条件が重なる場合は表や箇条書きに分ける。
- 「適切に」「必要に応じて」「速やかに」だけで済ませず、判断条件が確認できなければ未確認事項にする。

## 情報の順序

冒頭の1〜2文で、そのページの対象と分かることを示す。業務のページでは「何をする仕事か」を先に書く。背景や制度の説明は、読者がその結論を理解するために必要な範囲へ絞る。

業務プロセスでは、基本的に次の順で読めるようにする。

1. 目的と範囲、顧客が目指す状態
2. 開始条件
3. 関係者と役割
4. 必要な情報
5. 活動と判断
6. 残す成果
7. 前後業務への受渡し
8. 顧客の困りごとを確認する質問
9. 根拠と未確認事項

既存ページの統一された構成がある場合は、その構成を優先する。見出しを揃えること自体を目的にせず、同種のページを比較しやすくする。

## 本文に残す情報

本文に残すのは、業務の理解、適用条件、根拠の強さを判断するために必要な情報である。

次の内容は原則として本文から外す。

- この文書を作ることになった会議やIssueの経緯、分類案の比較、IDの採番方法
- 調査中に試した検索語や作業手順
- 執筆者向けのメモ
- 同じ免責や注意の繰り返し
- 読者の行動につながらない一般論

作成経緯や分類の選定理由を残す場合は、`maintenance/editorial-history.md` や対象のIssue・PRへ記録する。

ただし、資料の適用範囲、法令上の義務との違い、推測を避けるための限界説明は残す。一か所にまとめ、必要な場所から参照する。

## 表と箇条書き

- 比較、役割分担、入出力、分岐には表を使う。
- 順序がある場合だけ番号付きリストを使う。
- 箇条書きの各項目は同じ粒度と文型に揃える。
- 表のセルに長い背景説明を詰め込まない。共通する説明は表の前後へ出す。
- 大きな一覧は、分類ごとに短い表へ分ける。
- 列数が増え、スマートフォンで追いにくい場合は、情報を別の表か本文へ分ける。

## 根拠と断定

- 情報源に書かれた事実と、ガイドとして整理した関係を区別する。
- 一つの事例を、すべての建物に共通する手順として書かない。
- 法令、契約、個別運用の条件を混同しない。
- 不明な担当、期限、閾値、様式は推測せず、具体的な確認点として残す。
- `confidence` は文章の断定の強さと合わせる。

## 執筆・レビューの確認項目

- 冒頭と見出しから、このページで答える読者の疑問が分かるか。
- 営業・CS・商品企画・開発・事業責任者が、同じ業務と目指す結果を共有できるか。
- 顧客の担当範囲の前後にある依頼・承認・利用・費用判断へ進めるか。
- 作業完了、報告提出、問題解消を混同していないか。
- 未確認の顧客課題・効果・機能要件を事実として書いていないか。
- 会話・Issue・作成経緯・番号だけの参照を知らなくても読めるか。
- 同じ注意書き・一覧が重複していないか。見出しや表の各列に読者にとっての役割があるか。
- 根拠・適用範囲・未確認事項と、メニュー・一覧・本文の名称が保たれているか。

全ページを見直す場合は、対象のパスと、修正内容または問題なしと判断した理由を編集者向けの `maintenance/` に記録する。読者向け本文へレビューの進捗を載せない。
