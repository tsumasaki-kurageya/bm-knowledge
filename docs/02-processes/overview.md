# 建物維持保全の業務カタログ

## 目的と読み方

[DOMAIN-000：業務領域一覧](../01-domains/overview.md)の9領域に、主要業務22件を紐付けた初期カタログ。どんな業務が、何を受け取り、何を生み、次のどの判断へつながるかを俯瞰する。

本書のPROCESS-001は索引用IDであり、22件の業務には含めない。個別業務はPROCESS-002〜023。新しい業務は既存IDを再利用せず、続番で登録する。

1. 主領域から業務を探す。設備や会社ごとの一覧ではなく、成果を持つ仕事の単位で登録している。
2. 個別文書で目的・開始条件・入力・出力・役割・適用条件を確認する。
3. 「前後業務」のリンクから、受け渡す情報・判断を辿る。

本書の分類・入出力・関係は、公開資料の構成要素を横断した**整理案**。特定現場の実態、網羅的な法定業務一覧、詳細な標準作業手順を示すものではない。[BUSINESS-001](../00-business/overview.md)の目的・範囲を引き継ぐ。

## 業務関係の俯瞰

[PROCESS-024：業務関係とライフサイクル](lifecycle.md)で、定常・異常・中長期への還流を俯瞰できる。各Processの「遷移条件と受渡し」に条件・判断・情報の正本を置く。PROCESS-024は関係の索引で、主要業務22件には含めない。

## 初回の詳細化対象

Issue #6では、次の3件を詳細化する。選定基準は、複数の業務・Domainへの接続、実施前後の判断を理解する価値、公開一次資料の本文で確認できる具体性。実測の頻度・過去問い合わせ・訪問Evidenceは未収集であり、優先順位の根拠に使わない。SaaSの機能検討への有用性は期待であり、製品優先度が検証されたわけではない。

## 粒度と業務の性質

登録単位は「まとまりのある開始条件と成果を持ち、別の仕事へ引き渡せる業務」。機器ごとの測定点・清掃方法などはこの段階で分離しない。一方、測定結果を判定する仕事と状態を変える仕事は成果が異なるため分けた。

各Processの「業務の性質・適用条件」で次を区別する。これらを単一の必須・任意フラグへまとめない。

| 属性 | 記録する内容 | 例 |
| --- | --- | --- |
| 法令上の要求 | 適用対象・義務者・必要な行為・確認根拠。未確定なら未確認とする | PROCESS-013のうち適用法令に基づく点検 |
| 契約上の要求 | 約束した範囲・時期・品質・成果物・権限 | PROCESS-008で確認する履行条件 |
| 日常運用・任意の管理 | 利用条件や管理方針から行う仕事 | PROCESS-009の運転調整 |
| 発生契機・周期 | 日常・定期・臨時・変更・異常など | 同じ点検でも定期予定と災害後では契機が異なる |
| 実施形態 | 自営・委託・共同実施、依頼・判断・確認の役割 | PROCESS-005は自営にも必要な機能、PROCESS-006は委託時の仕事 |

新しい共通Frontmatter属性は追加せず、今回の適用条件は本文に記録する。建物の条件が分かった段階で具体化する。

## 用語と資料間の違い

| 用語・まとまり | 資料での扱い | カタログの扱い・未確認事項 |
| --- | --- | --- |
| 点検 | [D3](#d3)は状態の調査に加え、措置の要否判断を含める。日常・定期・臨時・法定は同じ分類軸ではない | PROCESS-013に状態評価を含む。法定点検と任意点検の適用条件は別記 |
| 保守 | [D3](#d3)は消耗品交換等の軽微な作業を扱う | PROCESS-010はこの狭い意味を出発点とする。「保守契約」の名称だけで修繕・点検を含む範囲は決めない |
| 修繕・更新 | [D8](#d8)は将来の工事・費用を計画する観点、[D3](#d3)は保守等の委託作業を扱う | PROCESS-004の将来計画とPROCESS-017・018の工事具体化・実施を分ける。修繕・改修・更新の厳密な同義性は確定しない |
| 環境衛生管理 | [D4](#d4)は空気・水・清掃・防除などを対象別にまとめる | 調べるPROCESS-014と、変えるPROCESS-009・011・012へ機能で対応付ける |
