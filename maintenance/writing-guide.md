# 読者向けガイドの書き方

建物維持保全に詳しくない人が、仕事の内容とつながりを理解できる文章にします。

- 冒頭に「何をする仕事か」を1〜2文で書きます。
- 見出しは「入力」より「必要な情報」、「終了条件」より「どこまでできれば完了か」のように、読者の疑問に合わせます。
- 専門用語が必要なら、初めに短く説明します。資料の正式名称・法令用語・引用の意味を変えません。
- 作成理由、Issueの進捗、分類案の比較、IDの採番方法などは、本文に混ぜず編集者向け資料やIssue・PRに記録します。
- 情報源、資料の適用範囲、未確認事項は本文に残します。読みやすくするために、不確かな内容を確定事項に変えません。
- 各業務の主領域は一つにし、他の関係する分類は関連領域として記録します。メニューは主領域から自動生成します。
- 一覧・分類・個別業務で同じ名前を使います。大きな一覧は分類ごとに短い表に分けます。
- 文書IDとURLを維持します。見出し名を変えた場合は、既存リンクのために旧見出しのアンカーを残します。

## メニューと文書の関係

| メニュー | Markdownの内容 |
| --- | --- |
| 全体像 | `docs/00-business/`：仕事の目的、関わる人、時間の流れ、参考資料 |
| 業務の分類 | `docs/01-domains/`：9分類の説明と個別業務へのリンク |
| 業務フロー | `docs/02-processes/`：一覧、業務のつながり、個別の22業務 |

業務フロー配下の分類名は、業務分類ページの見出しを使います。所属は個別業務の `- 主領域：[DOMAIN-xxx：…]` から読み取ります。主領域がない・複数ある・参照先がない場合はビルドを停止します。

ファイルの保存場所とURLは従来どおりです。メニューの階層はフォルダー名だけでなく、Markdownに書かれた分類関係を表します。

## 編集時の確認

`npm run build` で公開範囲と内部リンクを確認し、`npx playwright test` で検索・旧URL・スマートフォンのメニューを確認します。

作成時の選定理由は[編集経緯](editorial-history.md)を参照してください。
